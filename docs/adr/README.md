# Architecture Decision Records (ADRs)

Каждый ADR фиксирует одно архитектурное решение: контекст, выбор, последствия, альтернативы. Это даёт будущей команде понять «почему так», а не «что так».

## Когда писать новый ADR

- Выбор технологии, который сложно откатить (БД, фреймворк, очередь).
- Контракт между модулями/сервисами.
- Решение по безопасности или хранению данных.
- Любое «мы пробовали X, отказались по причине Y».

Не пишем ADR для тривиального — стиля кода, форматирования, имён переменных.

## Шаблон

```md
# ADR-XXXX: <короткий заголовок>

**Status:** Proposed | Accepted | Deprecated | Superseded by ADR-YYYY
**Date:** YYYY-MM-DD

## Context
Что происходит, какие силы давят на решение.

## Decision
Что выбрали (одно предложение, потом детали).

## Consequences
Что получаем (плюсы/минусы), что становится сложнее, что проще.

## Alternatives considered
Что отвергли и почему.
```
