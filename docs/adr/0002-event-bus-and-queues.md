# ADR-0002: In-process EventBus + BullMQ для фоновых задач

**Status:** Accepted
**Date:** 2026-04-27

## Context

Нужно решить два разных вопроса:

1. Как модули внутри монолита уведомляют друг друга о произошедших событиях (например, `booking.confirmed` → `notifications` отправляет уведомление).
2. Как выполнять долгие/ненадёжные операции (Telegram API, обработка видео, email-рассылки) без блокировки HTTP-запросов.

## Decision

- **Внутри процесса (синхронные домен-события):** `EventBus` поверх `node:events`. Модули `publish/subscribe` через константы из `domain-events.ts`.
- **Между процессами (тяжёлые задачи):** `BullMQ` поверх Redis. Очереди: `notifications`, `reminders`, `recordings`. Воркеры запускаются как отдельные процессы (см. `core/queue/workers/`).

## Consequences

**Почему два механизма:**
- EventBus — для дешёвой связности модулей, не пересекает границу процесса. Если модуль выделим в сервис, заменим имплементацию на брокер (Kafka/NATS), не трогая call-site'ы.
- BullMQ — для retry, backoff, delayed jobs, dead-letter и видимости (UI). Это инструмент исполнения, не транспорт событий.

**Правило выбора:**
- «Сообщить, что что-то произошло» → EventBus.
- «Сделать работу, которая может упасть и должна быть повторена» → BullMQ.

**Идемпотентность:** воркеры обязаны быть идемпотентными — BullMQ может повторять задачу при ошибке.

## Alternatives considered

- **Только Kafka/NATS:** избыточно на старте (доп. инфраструктура), даёт мало пользы пока всё в одном процессе.
- **Только setImmediate/setTimeout для асинхронщины:** теряем при рестарте процесса; нет retry, нет видимости.
