# ADR-0001: Модульный монолит вместо микросервисов на старте

**Status:** Accepted
**Date:** 2026-04-27

## Context

На старте проекта объём функциональности невелик (auth, users, lessons, bookings, notifications, recordings) и команда мала. Нужно выбрать между:
- **A.** Микросервисы с самого начала.
- **B.** Простой монолит без явных границ.
- **C.** Модульный монолит с чёткими границами модулей.

## Decision

Выбираем **C: модульный монолит**.

Каждый бизнес-модуль (`auth`, `users`, `lessons`, `bookings`, `notifications`, `recordings`) — это самостоятельный пакет внутри `apps/backend/src/modules/` с собственными слоями (entity, repository, service, controller, routes). Модули общаются через `EventBus` и публичные интерфейсы — никогда напрямую через внутренние классы.

## Consequences

**Плюсы:**
- Один деплой, один runtime, одна БД — низкая операционная сложность.
- Чистые границы — когда модуль перерастёт монолит, его можно вынести в отдельный сервис без переписывания: контракт уже определён через события.
- Не нужно управлять распределёнными транзакциями и сетевой надёжностью.

**Минусы:**
- Соблазн срезать углы и нарушить границы (нужна дисциплина в код-ревью).
- Все модули масштабируются вместе — пока нагрузка не критична.

## When to revisit

Извлекаем модуль в отдельный сервис, когда:
- его нагрузка отличается от остальных в 10x+,
- его данные не помещаются на одном инстансе Postgres,
- за него отвечает отдельная команда.

Прогноз: вероятно, первым выделится `notifications` (Telegram + push + email) или `video-call`/`recordings` (тяжёлый I/O).
