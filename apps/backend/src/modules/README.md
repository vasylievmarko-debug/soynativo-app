# Modules

Каждый модуль — это вертикальный срез функциональности (feature slice). Внутри
модуль выглядит почти как мини-приложение со своими слоями:

```
<module>/
├── <module>.entity.ts        # TypeORM сущность (Domain layer)
├── <module>.repository.ts    # Доступ к данным (Data layer)
├── <module>.service.ts       # Бизнес-логика (Application layer)
├── <module>.controller.ts    # HTTP handlers (Presentation layer)
├── <module>.routes.ts        # Регистрация маршрутов
├── dto/                      # Zod схемы и DTO
├── __tests__/                # Unit + integration тесты
└── subscribers/              # (опционально) обработчики domain events
```

## Правила зависимостей (направление импортов)

```
Controller → Service → Repository → Entity
                ↓
        EventBus (publish)
```

- **Controller** — только парсит вход, делегирует в Service, возвращает ответ.
- **Service** — содержит бизнес-логику, бросает `HttpException`, публикует события.
- **Repository** — единственный, кто знает про TypeORM и БД.
- **Entity** — чистая модель данных, без логики приложения.

## Общение между модулями

**НЕ** импортируйте сервис другого модуля напрямую (это создаёт циклические
зависимости и делает модули неотделимыми). Вместо этого:

1. **Domain Events** через `EventBus` — для уведомления о произошедшем
   (`booking.confirmed` → `notifications` создаёт уведомление).
2. **Public API модуля** — экспортируйте только то, что должно быть доступно
   снаружи (через `index.ts`). Внутренние классы оставляйте приватными.
3. **Очереди (BullMQ)** — для тяжёлых асинхронных задач (отправка Telegram,
   обработка видео, рассылка email).

## Когда выделять новый модуль

Создавай модуль, если функция:
- имеет собственную сущность БД, ИЛИ
- имеет собственные правила доступа, ИЛИ
- может в будущем стать отдельным микросервисом.

## Когда выносить модуль в микросервис

Этот монолит спроектирован как «модульный монолит» — каждый модуль может быть
извлечён, когда:
- нагрузка на него отличается от остальных в 10x+,
- его данные перестали умещаться на одном Postgres-инстансе,
- команда, отвечающая за него, выросла до отдельной.

До этого момента — оставляем в монолите. Это дешевле и быстрее.
